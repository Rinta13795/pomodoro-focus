## 1. 这份面经主要在考什么

### 1.1 结论

这份面经**主要考的是 `RAG + Agent 应用工程化能力`**，不是单纯考你知不知道几个大模型概念。

它的真实重心大致是：

1. `RAG` 链路是否真的做过
2. `Agent` 是否不仅会讲概念，还能讲执行逻辑
3. `memory / tool use / MCP` 是否能讲到设计层
4. 是否具备基本的后端 / 服务化 / 工程治理意识
5. 是否能把项目讲成“系统”，而不是讲成“调 API demo”

### 1.2 更具体的判断

这份面经的考察权重，我的判断如下：

- 最高权重：`RAG / Agent / memory / tools / MCP`
- 较高权重：`工程落地 / 服务化 / 安全 / 沙盒 / 流式输出`
- 中等权重：`项目表达`
- 较低权重：`Prompt Engineering`
- 很低权重：`大模型底层训练、微调、算法理论`

### 1.3 不要误判的地方

这份面经虽然表面上很多问题都围绕项目展开，但本质上不是在听你“讲做了什么”，而是在看：

- 你能不能解释**为什么这么设计**
- 你知不知道**出了问题该怎么排查**
- 你能不能回答**规模变大后怎么办**
- 你有没有意识到**企业环境下的治理、安全、权限、路由、审计**

一句话总结：

> 这份面经主要考的是“AI 应用系统设计能力”，不是“模型研究能力”。

## 2. 按主题拆解这份面经

## 2.1 RAG 数据处理

### 它是什么

包括：

- PDF 文本抽取
- 清洗噪声
- 合并错误断行
- chunk 切分
- OCR
- 表格 / 图片 / 图文混排处理

### 为什么会被问

因为很多 RAG 项目真正的问题，不在模型，也不在 embedding，而是在最前面的数据处理阶段。

很多人简历里写了 RAG，但实际上只是：

- 调 loader
- 调 splitter
- 调向量库
- 调模型回答

面试官问这些，就是想区分：

- 你是真的处理过真实数据
- 还是只做过教程级 demo

### 面试官真正想看什么能力

- 你有没有接触过真实脏数据
- 你是否理解“前面的抽取和清洗会直接影响后面的检索质量”
- 你是否知道复杂 PDF 不能只靠纯文本抽取

### 初学者视角下怎么理解

RAG 不是“把文件喂给模型”这么简单。  
前面的数据如果抽错、切坏、丢语义，后面检索和生成再强都救不回来。

## 2.2 RAG 检索、上下文与幻觉排查

### 它是什么

包括：

- chunk 太大或太小的取舍
- 召回条数控制
- rerank
- 上下文窗口裁剪
- 幻觉问题排查

### 为什么会被问

因为这是 RAG 里最核心的效果问题。

面试官不是只想知道你会不会说“减少幻觉”，而是要看你知不知道：

- 幻觉可能出在哪一层
- 应该按什么顺序排查

### 面试官真正想看什么能力

- 系统化排错能力
- 对 RAG 链路的拆解能力
- 是否能把问题归因到具体环节

### 初学者视角下怎么理解

如果模型答错了，不能一上来就说“模型不行”。  
应该顺着链路查：

1. 原始文档抽取对不对
2. chunk 有没有切坏
3. 检索有没有找错
4. rerank 有没有排错
5. prompt 有没有要求严格依据上下文
6. 最终回答有没有被模型自由发挥带偏

这类题其实在考：你有没有“工程排查脑子”。

- `RAGAS`

## 2.4 Agent 原理与编排

### 它是什么

如果结合 `nanobot` 源码来看，这一块更准确地说是：

- 以 `AgentRunner.run()` 为核心的工具循环
- LLM 决定是否发起 tool call
- 工具执行结果回填到消息历史
- 在外层加上 session、checkpoint、streaming、progress、pending injection 这些运行时机制
- 支持后台 subagent，但不是复杂的多 Agent 规划平台

### 为什么会被问

因为现在很多人会说自己“做了 Agent”，但很多项目其实只是：

- 一个 prompt
- 加几个工具
- 再跑个循环

面试官会继续追问，是为了看你有没有真正理解：

- 什么时候需要规划
- 什么时候任务应该拆开
- 什么时候并行才有意义

### 面试官真正想看什么能力

- 你是否真的理解 Agent loop
- 你是否知道工具调用链路是怎么串起来的
- 你是否知道“能跑”和“能长期稳定运行”之间差什么

### 初学者视角下怎么理解

如果只从 `nanobot` 源码出发，最稳的说法不是“它已经实现了完整规划”，而是：

- 它更像一个 `ReAct-like tool loop`
- 不是纯 workflow，因为下一步由模型根据当前上下文和工具结果继续决定
- 也不是完整的 `Plan-and-Execute`，因为源码里没有一个显式 planner 先产出全局计划再逐步执行

更贴源码的判断：

- **源码明确实现**
  - 工具循环：见 `nanobot/agent/runner.py`
  - 工具执行前后消息回填：见 `runner.py` 和 `loop.py`
  - 中途注入 follow-up message：见 `loop.py` 里的 pending queue
  - 后台 subagent：见 `nanobot/agent/subagent.py`
- **源码部分体现**
  - 并行：只对 `concurrency_safe` 的工具做批量并发执行
  - 子任务拆分：可以 `spawn`，但拆不拆主要还是靠模型和 prompt，不是显式调度器
- **源码没有明显实现**
  - 显式 planner
  - 任务图 / DAG
  - 多 Agent 间的复杂协商和冲突仲裁

面试最稳说法可以是：

> `nanobot` 的主干是一个带很多工程护栏的 Agent runtime，而不是一个完整的规划编排平台。

## 2.5 Hook / Skill

### 它是什么

- `hook`：代码级生命周期扩展点
- `skill`：基于 `SKILL.md` 的能力说明包，由系统发现、摘要、按需加载

这两个东西在 `nanobot` 里不是一回事。

### 为什么会被问

因为这是从“能跑”走向“可维护”的一步。

### 面试官真正想看什么能力

- 抽象能力
- 系统可扩展性意识
- 是否能区分“运行时扩展”和“prompt 侧能力注入”

### 初学者视角下怎么理解

结合 `nanobot` 源码，更贴切的理解是：

- `hook` 解决的是 runtime 生命周期问题  
  例如：
  - `before_iteration`
  - `before_execute_tools`
  - `after_iteration`
  - `on_stream`
  - `on_stream_end`

- `skill` 解决的是 prompt 能力组织问题  
  例如：
  - 自动注入 `always: true` 的 skill
  - 把其他 skill 做成索引摘要
  - 需要时再通过 `read_file` 读取具体 `SKILL.md`

更贴源码的判断：

- **源码明确实现**
  - hook 接口：`nanobot/agent/hook.py`
  - hook 组合器：`CompositeHook`
  - skills loader：`nanobot/agent/skills.py`
  - memory skill / my skill 作为 always skills 注入 system prompt
- **源码部分体现**
  - skill 可以附带 metadata、requirements、脚本、references
  - workspace skill 可以覆盖 builtin skill
- **源码没有明显实现**
  - skill 不是可直接执行的“tool”
  - skill 不是复杂插件运行时

面试最稳说法：

> 在 `nanobot` 里，hook 更像运行时插桩点，skill 更像能力文档和操作规范包。前者是代码机制，后者是 prompt 机制。

## 2.6 Memory / 记忆机制

### 它是什么

如果结合 `nanobot` 源码，这一块应该拆成 3 层：

- `session.messages`：当前会话的短期上下文
- `memory/history.jsonl`：压缩后的中间历史层
- `SOUL.md / USER.md / memory/MEMORY.md`：长期知识文件

另外还有两个关键机制：

- `Consolidator`：在上下文窗口吃紧时，把旧会话压缩到 `history.jsonl`
- `Dream`：慢速地把 `history.jsonl` 中的新内容整理进长期记忆文件

### 为什么会被问

因为 memory 是 Agent 很关键的部分，也是最容易被“嘴上会说、实际上没做”的部分。

### 面试官真正想看什么能力

- 你是否真的做了分层
- 你是否知道短期上下文和长期知识不能混成一团
- 你是否知道“压缩、归档、整理”是不同动作
- 你是否会把源码里没有的能力讲过头

### 初学者视角下怎么理解

如果只按 `nanobot` 源码讲，最稳的是下面这套：

- **短期记忆**
  - 就是 `session.messages`
  - 当前请求真正回放给模型的主要也是它

- **中间历史层**
  - 不是所有旧对话都继续塞上下文
  - `Consolidator` 会把旧消息摘要后写进 `memory/history.jsonl`

- **长期记忆**
  - `Dream` 再从 `history.jsonl` 提炼，更新：
    - `SOUL.md`
    - `USER.md`
    - `memory/MEMORY.md`

更贴源码的判断：

- **源码明确实现**
  - 短期记忆：`nanobot/session/manager.py`
  - 长期记忆文件：`nanobot/agent/memory.py`
  - `history.jsonl` 光标、追加、压缩：`MemoryStore`
  - token 压缩：`Consolidator`
  - 两阶段长期整理：`Dream`
  - 自动 idle compact：`AutoCompact`
- **源码部分体现**
  - “热记忆 / 冷记忆”这个说法可以类比到 `session.messages` vs `history.jsonl + 长期文件`
  - “记忆污染”有一定防护，例如：
    - `strip_think`
    - 对空泄漏内容不回写
    - 对超大 history entry 做截断
- **源码没有明显实现**
  - 向量数据库式长期记忆检索
  - 多 Agent 共享记忆服务
  - 细粒度权限隔离
  - 复杂记忆冲突消解

所以你现在最不该讲太满的地方是：

- “nanobot 已经做了长期记忆检索”
- “nanobot 已经做了多 Agent 共享记忆”
- “nanobot 已经做了成熟的记忆污染治理平台”

最多只能说：

> 它已经实现了比较清晰的分层记忆落盘和整理机制，但不是完整的共享记忆 / 检索型 memory 系统。

## 2.7 MCP / tools / function calling / skill

### 它是什么

- `function calling`：provider 把模型产出的调用意图解析成统一的 `ToolCallRequest`
- `tool`：`ToolRegistry` 里注册的可调用能力
- `MCP`：把外部 server 的 tools / resources / prompts 封装进本地 tool 系统
- `skill`：不是执行单元，而是 prompt 能力说明包

### 为什么会被问

因为现在这块很热，但很多人概念混着说。

### 面试官真正想看什么能力

- 概念是否清楚
- 你是否知道工具调用链路从哪里开始、到哪里结束
- 你是否知道 tool context、tool execution、MCP 包装之间的关系
- 你是否会把“支持 MCP”说成“已经做了复杂 MCP 平台治理”

### 初学者视角下怎么理解

结合 `nanobot` 源码，最稳的理解是：

- provider 层先把不同厂商的 function calling 统一成 `ToolCallRequest`
- `ToolRegistry` 负责：
  - 注册工具
  - 暴露 schema
  - 参数 cast / validate
  - 执行
- `AgentLoop` 在执行前会把 routing context 注入到部分有状态工具里
  - `message`
  - `spawn`
  - `cron`
  - `my`
- MCP 则是把远端能力包装成：
  - `MCPToolWrapper`
  - `MCPResourceWrapper`
  - `MCPPromptWrapper`

更贴源码的判断：

- **源码明确实现**
  - tool schema / 校验 / 执行：`nanobot/agent/tools/base.py`、`registry.py`
  - tool context 注入：`loop.py` 的 `_set_tool_context`
  - MCP 连接：`nanobot/agent/tools/mcp.py`
  - 支持 `stdio / sse / streamableHttp`
  - `resources` 和 `prompts` 也会被注册成 tool
- **源码部分体现**
  - tool 顺序有稳定策略：内置工具在前，MCP 工具在后
  - `enabledTools` 可以做过滤
  - 某些工具上下文通过 `ContextVar` 做隔离
- **源码没有明显实现**
  - 语义级 tool routing
  - 根据问题动态召回 top-k tool schema
  - 企业级 MCP 网关、注册中心、审计平台

所以面试时你可以讲：

> `nanobot` 的重点不是“我接了 MCP 这个词”，而是它把 MCP server 暴露出来的 tool/resource/prompt 统一进了本地 tool 调用链。

但不要讲成：

> 它已经做了完整的 MCP 平台治理和复杂 tool routing。

`这是推测：` 如果你这里说的 `nanobots`，实际上已经包括了阅读 `nanobot` 的核心源码，那你能覆盖的内容会比“只会用框架”更扎实。

- “你做过 Agent 吗”

- “session 和 memory 是怎么分层的”
- “为什么要做 checkpoint 和恢复”

但是，这通常还不等于你能顶住深入追问。

## 3.2 你大概率还不会的部分

`这是推测：` 你现在大概率薄弱的地方在下面这些：

- 真实 `RAG` 数据清洗和复杂 PDF 处理
- chunk 策略背后的取舍
- rerank 的作用和接入点
- 幻觉排查链路
- 评测体系，比如 `RAGAS`
- 企业级长期记忆写入策略与污染治理
- 复杂多 Agent 规划和协作
- 企业级 `MCP` 治理

- `nanobot` 的 memory 做得不浅，但它不是检索式长期记忆系统

- `nanobot` 支持 MCP，但不等于已经做了复杂 tool routing 和平台治理

## 3.3 你现在去答会比较虚的问题

下面这些题，你如果现在直接去答，大概率会虚：

- “RAG 幻觉怎么排查”
- “为什么 chunk 太大或太小都不行”

- “为什么用 SSE，不用 WebSocket”
- “Agent 沙盒怎么设计”
- “为什么选 Chroma，不选 FAISS / Milvus”

另外有一些题你可以答一部分，但不能答太满：

- “长期记忆怎么做”
  - 你可以讲 `session.messages -> history.jsonl -> Dream files`
  - 但不要讲成“我们已经做了向量检索式长期记忆”
- “多 Agent 怎么做”
  - 你可以讲 `spawn` 和后台 subagent
  - 但不要讲成“我们已经做了完整规划和协同平台”
- “MCP 怎么做”
  - 你可以讲连接和 wrapper
  - 但不要讲成“我们已经做了复杂注册中心和语义路由”

这些题的共同点是：  
它们不只考概念，而是考你有没有做过系统层面的思考。

## 5. 这份面经对我后续学习路线的指导意义

## 5.1 后面应该优先补什么

我的建议顺序是：

1. 先把 `nanobot` 里已经实现的 Agent runtime 吃透
2. 再单独补 `RAG`
3. 再并行补“和 Agent 最相关的后端基础”
4. 最后再系统补更完整的八股和工程化知识

## 5.2 是先补 LLM / Agent 基础，还是先补后端，还是先补八股

我的判断：

- 不是先死磕大模型底层
- 也不是先刷一大堆泛后端八股
- 也不要误以为“学了 nanobot 就等于学完了 RAG”
- 最优顺序是：

`先读懂 Agent runtime -> 再补 RAG -> 再补直接相关的后端基础 -> 再补泛八股`

原因很简单：

- `nanobot` 最强的不是 RAG，而是 Agent runtime
- 这份面经又不只是问“模型原理”，更在问“系统怎么跑”
- 所以你当前最有把握补实的，是 `Agent runtime + 工程护栏`

## 5.3 哪些知识点是连接 Agent 和后端的关键桥梁

这是你后面最该重视的一段。

### `HTTP / API`

因为：

- tool 调用靠接口
- 模型服务靠接口
- 前后端交互靠接口

不会接口，就很难把 Agent 讲成产品系统。

### 异步任务

因为：

- Agent 经常是慢任务
- 工具调用可能超时
- 多步骤任务不适合全都同步阻塞

`nanobot` 源码里能对应上的抓手：

- `MessageBus`
- `pending queue`
- 后台 `subagent`
- 中断恢复

### 数据库

因为：

- 会话状态要存
- 任务状态要存
- 长期记忆要存
- 日志和结果也可能要存

`nanobot` 当前更多是：

- JSONL session
- `history.jsonl`
- Markdown memory files

所以数据库这块不是源码现成教给你的，而是你后续要自己补的延展方向。

### 缓存

因为：

- 一些重复查询结果可以复用
- 热门上下文或用户信息可以减少重复计算

### 队列

因为：

- 长任务可以异步化
- 工具调用可以解耦
- 高并发下可以削峰

### 评测 / 日志 / Trace

因为：

- 没日志就难排错
- 没 trace 就看不清链路
- 没评测就不知道优化是否有效

`nanobot` 已经有一点偏 runtime 观察性的东西：

- progress events
- tool events
- checkpoint
- token usage

但还不是完整 observability 平台。

### 部署 / Docker / 沙盒

因为：

- AI demo 能跑不等于能上线
- Agent 一旦能执行操作，就必须考虑隔离和权限

这块 `nanobot` 源码里能看到真实工程味的地方有：

- `exec` 的 deny patterns
- workspace 限制
- `bwrap` sandbox
- `SECURITY.md` 里的部署建议

## 5.4 这份面经对你的路线给出的最强信号

最强信号其实是：

> 想投 Agent / AI 工程实习，不能只学“模型怎么调用”，还必须学“Agent runtime 怎么稳定运行，以及后端系统怎么承载这种 runtime”。

## 9. 把面经问题改写成更真实的面试问法

下面这些问法，比原始整理版更像真实面试。

## 9.1 RAG 相关

- “你这个 `RAG` 里最难处理的数据是什么？最后怎么清洗的？”
  - 在考：你有没有接触真实脏数据

- “为什么 chunk 要这么切？切大一点或小一点分别会出什么问题？”
  - 在考：你是否理解 chunk 的 trade-off

- “如果文档里写的是 15 天年假，模型答成 10 天，你会怎么排查？”
  - 在考：你是否具备链路排错能力

- “你为什么需要 rerank？不做会怎样？”
  - 在考：你是否理解召回后排序的问题

- “你怎么判断 `RAG` 变好了，不是你的主观感觉？”
  - 在考：你是否有评测意识

## 9.2 Agent 相关

- “你做的到底是 workflow，还是 Agent？边界在哪？”
  - 在考：你对 Agent 的定义是否清楚

- “你们的 Agent 是自己规划，还是你们把流程写死了？”
  - 在考：执行控制权在谁手里

- “为什么这里需要 Agent，不直接写死流程？”
  - 在考：技术方案选择能力

- “多 Agent 并行后，如果结果冲突，你怎么处理？”
  - 在考：协作与结果汇总设计

## 9.3 Memory 相关

- “长期记忆到底存什么？什么绝对不该存？”
  - 在考：记忆治理能力

- “长期记忆什么时候写入？谁来决定写不写？”
  - 在考：状态管理和写入策略

- “如果记错了怎么办？长期记忆怎么更新或删除？”
  - 在考：你是否考虑过纠错机制

## 9.4 Tools / MCP 相关

- “`function calling`、tool use、`MCP`，你怎么区分？”
  - 在考：概念是否清楚

- “工具很多时，模型怎么知道该选哪个？”
  - 在考：工具路由和按需加载

- “如果工具调用失败、超时、返回脏数据，怎么兜底？”
  - 在考：鲁棒性设计

- “如果以后要接 100 个 MCP 服务，你会怎么管理？”
  - 在考：平台化治理意识

## 9.5 工程化 / 后端相关

- “前端为什么用 `SSE`，不用 `WebSocket`？”
  - 在考：通信方式选型

- “这个系统的后端接口大概怎么设计？”
  - 在考：你能否把 AI 应用讲成服务

- “如果并发变高了，你觉得最先会出问题的是哪一层？”
  - 在考：性能瓶颈意识

- “代码执行类 Agent 为什么一定要沙盒？”
  - 在考：安全意识

- “如果让你把这个系统放到企业里，你最担心什么？”
  - 在考：工程风险判断
